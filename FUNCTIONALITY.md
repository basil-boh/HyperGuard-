# HyperGuard — Functionality Report

An honest audit of what is built, what is simulated, what is decorative, and what breaks.
Written by reading every code path and running the system, not from the README.

**Verdict:** the skeleton is real and better than most hackathon projects — a genuine LangGraph
state machine, a genuine risk model, a genuine bank, genuine outbound calls, genuine LLM
adjudication, 72 passing tests. The gap between the pitch and the code is narrower than usual.
But there are three places where a judge or an engineer would catch you, one of which is a
false claim in the demo script, and the system has a structural flaw that makes every
intervention end in a block regardless of what the customer says.

## The structural issue: two paths that behave differently

This is the most important thing to understand about the codebase, and it is not in the README.

**Path A — simulated (no Twilio, or no `PUBLIC_BASE_URL`).** The graph runs end to end.
The negotiator speaks, and then `VictimSimulator` replays the seeded archetype's script as
the customer's reply (`negotiator.py:68-71`). The Educator keyword-matches that script and
recovers the archetype it was generated from.

> **The classification cannot fail, because the input was generated from the answer.**
> `seed.py` printing `scam: Government / Police Impersonation` is this loop closing on itself.
> It demonstrates that the orchestration is wired correctly. It demonstrates nothing about
> whether the classifier works.

**Path B — live (Twilio + a reachable `PUBLIC_BASE_URL`).** The negotiator places the call and
immediately returns `awaiting_live: True`, and the graph **routes straight to the Arbiter,
skipping the Educator and Guardian entirely** (`graph.py:97-101`). The real conversation happens
over webhooks; classification, guardian escalation and the report run afterwards in
`finalize_followup`.

So on the live path the swarm decides **on the risk score alone**, before anyone has said
anything. That's why running `seed.py` with the real `.env` prints `scam —` and `guardians 0`
while the no-keys run prints the full result. Both are correct behaviour for their path — but
only one of them is the product being pitched.

## Where it breaks

### 1. Scenario persistence fails 100% of the time — BROKEN

`SupabaseStore.save_outcome` writes `user_id = customer.id`, but `cases.user_id` has
`references users(id)` (`backend/db/schema.sql:80`). Scenario personas are `cust_may` /
`cust_daniel`, which live in a different table. Observed on every run:

```
Persisting case HG-43FF54F65E failed: insert or update on table "cases" violates foreign
key constraint "cases_user_id_fkey" — Key (user_id)=(cust_may) is not present in "users".
```

Four scenarios, four failures. Silent — it's a `logger.warning`, and the swarm carries on.
Every console-launched scenario case is lost on restart.

### 2. Every intervention blocks, and nothing can un-block it — DESIGN FLAW

The Arbiter's fallthrough is `block` ("inconclusive on a high-risk transfer → protect first",
`arbiter.py:47-48`). On the live path, `verification` is never set to `verified`, because the
Educator never ran. So:

> **Any transfer scoring ≥ 0.58 on the live path is blocked before the customer speaks a word.**

Then `finalize_followup` runs the LLM, which may conclude `recommended_action: "clear"` — and
**nothing happens with that**. There is no un-block path anywhere in the backend, frontend or
mobile (verified by search). A customer who perfectly explains a legitimate transfer stays
blocked forever. Your own pitch answers *"Won't it annoy legitimate users?"* with "low-risk
transfers clear instantly" — true, but any false positive above 0.58 is permanent.

### 3. A stale `PUBLIC_BASE_URL` silently disarms the whole system — FAILURE MODE

`interactive_enabled` requires `telephony_enabled AND public_base_url`. If that ngrok URL is
dead (which it will be, tunnels rotate), Twilio can't fetch the TwiML — but the negotiator has
*already* returned `awaiting_live: True`. Result: no conversation, no classification, no guardian
alert, no follow-up, and a case decided on the risk score with an empty transcript. Nothing in
the UI distinguishes this from a working intervention.

### 4. The Twilio webhooks are unauthenticated — SECURITY

`/twilio/voice/start` and `/twilio/voice/answer` do no signature validation (no
`RequestValidator`, no `X-Twilio-Signature` check). `case_id` comes from a query parameter.
Anyone who knows or guesses a case ID can POST arbitrary "customer answers" into a live case,
which then feed the LLM adjudicator, the guardian SMS and the incident report.

### 5. The live deployment is running with development defaults — SECURITY

`/api/health` on Railway reports `"environment": "development"`. That matters:
`auth_signing_key` falls back to the public hardcoded key
`hyperguard-dev-signing-key-do-not-use-in-production`, **and the warning is suppressed**
because the warning only fires when environment is *not* development. Separately,
`expose_demo_credentials` defaults to `True`, so
`GET /api/auth/demo-accounts` currently serves phone numbers and PINs for every seeded account
to the public internet. Fake money, so it's not an emergency — but it is the first thing a
bank's security reviewer would find.

### 6. Follow-up is fire-and-forget — RELIABILITY

`asyncio.create_task(finalize_followup(case_id))` (`twilio_voice.py:114`) with no done-callback.
If it raises, the exception is swallowed and the case silently never gets its assessment,
guardian alert or report. It dies with the process, has no retry, and cannot survive a redeploy
mid-call.

### 7. Single-process by construction — SCALING

`InterventionRegistry` is an in-memory dict capped at 200 cases, fed by an in-process bus
subscription. Two uvicorn workers means the console subscribed to worker A never sees worker B's
events, and `finalize_followup` can't find its case bucket. The Redis mirror doesn't help
because nothing consumes it.

### 8. Schema drift — DOCS

`infra/schema.sql` (90 lines, a `customers` table) is stale. The code uses
`backend/db/schema.sql` (174 lines: `users`, `recipients`, `contacts`, `transactions`, `cases`,
`guardian_links`, `incident_reports`, `authority_filings`). The README points people at the
wrong one, so anyone following setup instructions provisions a database the app can't use.

## Honesty audit

Four claims that didn't survive contact with the code. **All four are now fixed** — the
findings are kept below because the reasoning is the useful part, and because the same trap
reappears every time a feature ships ahead of its documentation.

**1. The landing page's "live interceptions feed" is fabricated.** `InterceptionFeed.tsx` picks
a random scam name and a random amount every 2.6 seconds, from a counter seeded at `1284`. The
source comment says so plainly: *"sampled at random for the live feed."* As a landing-page
animation that's completely normal. The problem is `PRESENTATION.md` §2, which instructs you to
point at it and say:

> *"This is the swarm working in real time — every row is a scam caught mid-payment and blocked."*

That is a false statement of fact to judges, and it's the one thing here that could actually
cost you. Everything else in your demo is real enough to defend.

> **FIXED.** The panel now carries an `Illustrative` chip in its header, its status light reads
> `Demo` instead of `Rec`, the counter is labelled *Sample volume* rather than *Intercepted
> today*, and a caption under the panel reads "Illustrative simulation of the interception
> pattern — not live customer data." `PRESENTATION.md` §2 and fallback #3 now say so out loud.

**2. "The Educator classifies the scam with AI."** It's substring matching. The archetype library
is genuinely well-researched and the counter-lines are good, but the mechanism is keyword
density. Call it a "scam-pattern classifier" and you're fine; call it AI and someone will read
`scam_taxonomy.py`.

> **FIXED.** The README's Educator section now states the mechanism outright — indicator-density
> classifier, not an LLM — explains *why* the counter-lines are authored rather than generated,
> and points at `services/reasoning.py` as where the LLM's judgement actually enters. This is the
> stronger claim anyway: it's the same argument the Digital Twin section already makes well.

**3. "Redis Streams event bus."** It's a write-only mirror. Calling it a distributed bus in the
README is wrong.

> **FIXED.** The `REDIS_URL` row now reads "mirrors every swarm event to a Redis stream, for audit
> and replay", and says explicitly that nothing consumes the stream yet so it does not make the
> app multi-worker.

**4. "An LLM explainer turns the risk signals into human-readable reasons."** From
`PRESENTATION.md`'s judge Q&A — the worst place to be wrong. There is no LLM anywhere in the risk
path; `RiskEngine._rationale` is a static method that formats the signals it just computed. The
reasons are real and human-readable, they're just written by code.

> **FIXED.** The Q&A answer now describes the logistic model with legible weights and per-signal
> written reasons, and leans on *deliberately not a black box* — which is the better answer to
> that question regardless. The adjacent "won't it annoy legitimate users?" answer no longer
> cites the illustrative feed as evidence; it points at the seeded-account contrast you can
> actually demonstrate, and concedes up front that there's no measured false-positive rate yet.

Worth noting on the other side: the code is *more* honest than the docs in places.
`followup.py:124` explicitly comments that no police API exists. `config.py` documents the
capability-gating design carefully. Whoever wrote the docstrings was not trying to fool anyone.

## Honest limitations

- **Nothing has been evaluated.** There is no labelled dataset, no precision/recall for the
  classifier, no measured false-positive rate for the 0.58 threshold. The thresholds `0.58` and
  `0.88` are chosen constants, not tuned ones. You cannot currently answer "how often does this
  block a legitimate transfer?" — and that is the only question a bank actually cares about.
- **The live conversation is 3 fixed questions.** It does not adapt, cannot follow up on an
  interesting answer, and cannot handle a hostile or confused caller.
- **English only, `en-SG` speech recognition, one voice.** Real elderly Singaporean scam victims
  frequently speak Mandarin, Hokkien, Malay or Tamil. This is a large gap for the stated user.
- **The scammer is assumed to be gone.** Real APP fraud often has the scammer on the other line
  coaching the victim through the bank's call. Nothing models that.
- **No human-in-the-loop.** The console is read-only; a fraud analyst cannot intervene, override,
  or release.
- **Two lost paths for the money.** There's no ledger reconciliation and no settlement
  integration — blocking is a status change on a row.

## What's next — concrete plan

Ordered by what a sceptic would attack first.

### P0 — before you show this to anyone else (~half a day)

1. **Fix the demo script.** Change `PRESENTATION.md` §2 to describe the feed as illustrative.
   One sentence. Removes your only real credibility risk.
2. **Lock the deployment.** Set `ENVIRONMENT=production`, `AUTH_SECRET=<random 32 bytes>`,
   `EXPOSE_DEMO_CREDENTIALS=false` on Railway.
3. **Validate Twilio signatures.** `twilio.request_validator.RequestValidator` against
   `X-Twilio-Signature` on both webhook routes. ~15 lines.
4. **Fix the schema pointer.** Delete `infra/schema.sql` or regenerate it from
   `backend/db/schema.sql`; update the README.
5. **Fix the case FK.** Either upsert a `users` row for scenario personas before saving, or drop
   the FK on `cases.user_id`. Currently 100% of scenario cases fail to persist.

### P1 — make the live path match the pitch (~2 days)

6. **Let the follow-up reverse a block.** When `recommended_action == "clear"`, release the
   transfer, emit a `decision_revised` event, and update the case. This closes the
   false-positive trap and is the single highest-value fix in this list — it's the difference
   between "blocks everything" and "adjudicates".
7. **Make the interview adaptive.** Replace the 3 hardcoded questions with an LLM-generated next
   question conditioned on the answers so far, keeping a hard cap on turns and keeping the
   authored safety lines verbatim. The plumbing already exists in `dialogue.py`.
8. **Classify with the LLM, keep keywords as the floor.** Mirror the risk engine's philosophy:
   the LLM proposes the archetype, the keyword matcher is a deterministic floor that can only
   make it stricter. Same shape as the Arbiter's existing bias-to-safety.

### P2 — make it survive (~2 days)

9. **Persist the registry.** Move `InterventionRegistry` behind Redis or Postgres so follow-up
   survives a restart and more than one worker.
10. **Actually consume the Redis stream** (`xreadgroup`), or delete the claim and the capability
    flag.
11. **Make follow-up durable.** Give the task a done-callback that logs, add a retry with
    backoff, and write a `followup_pending` flag so a restart can resume.
12. **Detect the disarmed state.** If `PUBLIC_BASE_URL` doesn't answer a health probe at startup,
    refuse to set `interactive_enabled` and log loudly — falling back to the simulated path is
    strictly better than a silent no-op intervention.

### P3 — the thing that makes it a product (~1 week)

13. **Build an evaluation set.** 100–200 labelled transcripts — real scam narratives from SPF /
    ScamShield public advisories, plus legitimate high-value transfers. Measure classifier
    precision/recall and the arbiter's false-positive rate at the current thresholds.
14. **Tune 0.58 and 0.88 against that set** instead of intuition, and publish the curve.
15. **Then** the pitch gets its missing sentence: *"we block 9 of 10 scams and interrupt 1 in
    N legitimate transfers"* — which is the only claim a bank will actually buy.

### Deliberately not next

Temporal, multi-language, media-stream transcription, and the recall/settlement integration are
all real work, but none of them change whether the core claim is true. Do P3 first.
